# 08 — Troubleshooting

## Гроші: що кит робить безкоштовно, а що ні

🔴 Найдорожче непорозуміння (зловлене на живій установці 22.08.2026): «кит стоїть,
значить агент читає все локально й безкоштовно». Це не так, і ось межа.

| Що | Чим виконується | Ціна |
|---|---|---|
| Ембединг запиту й фрагментів, векторний пошук, авто-пригадування у хуку | локальна Ollama (bge-m3) | **$0**, з машини нічого не виходить |
| Індексація архівів (навіть сотні тисяч фрагментів) | те саме | **$0** |
| Читання агентом знайденого файла, роздуми, відповідь тобі | твій агент (Codex/Claude) | **твої токени / кредити** |

Тобто кит ріже не ціну відповіді, а **обсяг того, що агент мусить прочитати, щоб
відповісти**: замість «прочитай 40 файлів» — «ось 3 доречні фрагменти». Наказ
«читай усе через Ollama» неможливо виконати: Ollama тут рушій пошуку, а не той,
хто тобі відповідає.

Що дійсно економить ліміти: `/compact` до того, як контекст роздувся; вузький
скоуп задачі; питати ім'я файла, а не «переглянь усе». Див. docs/07.

## Ollama / embed

- **`search` падає «Ollama недоступний»** → два виходи: 🙋 запустити застосунок
  Ollama (або `ollama serve`; перевірка: `curl -s localhost:11434/api/tags`) АБО
  перейти на варіант A (OpenRouter): `openrouter_enabled=true` у config.toml + ключ —
  тоді Ollama взагалі не потрібна (див. docs/04).
- **«Складно з Ollama» на macOS** → GUI-панель
  [KobzarAI](https://github.com/steptonite/KobzarAI) керує Ollama-моделями без термінала.
- **Нема моделі bge-m3** → `ollama pull bge-m3` (≈1.1 ГБ разово). Модель має бути
  ТА САМА для індексації і пошуку — інші embedding-моделі несумісні по векторах
  (доведеться повний реіндекс).
- **Повільно на слабкому Mac** → нормально: пошук ~0.5–6 с; перший індекс великого
  архіву — хвилини-години. Індексуй по одному source, не all.
- **Перемикання Ollama ↔ OpenRouter** → просто зміни `openrouter_enabled` у
  config.toml (ключ: env `OPENROUTER_API_KEY` або env_file). Та сама модель
  `baai/bge-m3` обидва боки → реіндекс не потрібен.

## Конвертери

- **`conversations.json not found`** → перевір, що `--src` вказує на РОЗПАКОВАНУ
  теку експорту (не на zip і не на батьківську теку).
- **Gemini: 0 сесій** → перевір шлях `My Activity/Gemini Apps/MyActivity.html`
  усередині Takeout; мова акаунта Google може міняти назви тек — знайди html через
  `find Takeout -name "MyActivity.html"`.
- **Битий/обрізаний json** → перекачати експорт; конвертери не лікують биті файли
  (сире = першоджерело, його не можна «доправляти»).
- **Повторний прогін щось «пропустив»** → це норма: hash збігся, файл не змінювався.

## Індекс

- **`database is locked`** → у WAL-режимі рідкість; перевір, чи не висить старий
  процес індексації (`ps aux | grep librarian`). Дочекайся або вбий.
- **Індекс роздувся / сміття від видалених файлів** → найпростіше: видалити
  `index.db*` і переіндексувати all (локально = $0, лише час).
- **Search знаходить не те** → перевір `stats`: чи проіндексоване потрібне джерело;
  спробуй 2-3 формулювання запиту синонімами; звузь `--source`.

## Хуки

- **Хук не спрацьовує** → шляхи в settings.json мають бути АБСОЛЮТНІ (без ~);
  перевір `python3 <шлях>/semantic_recall.py </dev/null` — має мовчки вийти.
  Після зміни settings.json потрібна нова сесія.
- **«validation failed» від PreCompact** → у stdout PreCompact-хука щось потрапило;
  він має бути німим (див. коментар у pre_compact.sh).
- **Машина гріється / вентилятори виють під час стиснення контексту** → PreCompact
  запускає фонову індексацію транскриптів. До 22.07.2026 хук не мав локу: довга
  сесія з багатьма стисненнями підряд накладала прогони один на одного, і вони
  паралельно молотили embed-модель. Полагоджено атомарним mkdir-локом
  (`$TMPDIR/sbkit-index.lock`, осиротілий знімається через 30 хв). Якщо
  оновлюєшся зі старішої версії — обов'язково підтягни `scripts/hooks/pre_compact.sh`.
  Замок можна зняти руками: `rmdir "$TMPDIR/sbkit-index.lock"`.
- **`index.db-wal` розрісся на сотні мегабайт** → до 22.07.2026 чекпоінт WAL не
  робився ніде, і файл ріс безмежно — на великій базі він здатен перегнати
  сам файл індексу. Тепер `index`
  завершується `PRAGMA wal_checkpoint(TRUNCATE)`. Разово після оновлення WAL
  зіллється сам на першій же індексації.
- **semantic_recall шумить нерелевантним** → не тюнінгуй regex/dist у хуку: confidence
  приходить із retrieval-core. Порівняй `--retrieval vector|hybrid`, перевір trust/source,
  stopwords і golden-набір; raw-результат не повинен ставати сильним якорем.
- **`semantic recall unavailable`** → деталь лежить у
  `~/.config/second-brain/logs/semantic_recall.log`; перевір Ollama/config і ручний
  `librarian.py search ... --format json`.

## Obsidian

- **Не бачить symlink-тек** → Obsidian підтримує symlinks; перевір що vault відкрито
  САМЕ в `vault.root`, а не в одній з підтек. Graph view: увімкни «Existing files only».
- **Wikilink на чат не резолвиться** → лінк має бути на basename файлу без .md
  (`[[2026-06-01_Назва_abc123]]`), файл — усередині vault (через symlink архіву).

## Загальний принцип

Сирі шари (експорти, конвертовані чати) — незнищенні першоджерела: будь-який
зламаний похідний шар (індекс, самарі, symlinks) відновлюється з них заново.
Паніка недоречна; видаляти сире — злочин.
