# Канон структури Другого мозку

Правила, за якими тримається граф. Будь-яка нота будь-якої моделі має цього
дотримуватись, інакше бази роз'їжджаються об криву основу. (Скопіюй цю ноту в
memory-теку як `ref_memory_vault_canon.md` — щоб канон був у самій базі.)

## 1. Master-vault

ОДИН Obsidian-vault через symlinks (файли фізично лишаються на місцях):
memory + архіви чатів + `inbox/` (реальна тека для сирих надиктовок).
Точка входу людини — `_HOME.md`; точка входу моделі — `memory/MEMORY.md`.
⚠️ НЕ переносити файли фізично, НЕ міняти шляхи в config без реіндексу.

## 2. Іменування (memory-тека, пласка)

- **snake_case** завжди (`project_garden.md`, не `project-garden.md`).
- Префікс за типом: `project_` · `feedback_` · `ref_` · `issue_` · `idea_` · `user_` · `hub_`.
- `name:` у frontmatter == імені файлу без `.md` (перевіряється sanitize --audit).
- Хаби: `hub_<домен>`, 3–6 штук під домени життя користувача.

## 3. Frontmatter-канон

```yaml
---
name: <snake_case == імені файлу>
description: <один рядок — для семпошуку і людини>
metadata:
  type: user | feedback | project | reference | idea | issue
---
```

## 4. Wikilink-політика

- Ноти між собою: `[[назва_ноти]]`.
- Крос-базові (memory → чат-архів): wikilink на basename чат-файлу — резолвиться
  в master-vault.
- Директорії та скіли — бектики (`chats`, `lean-mode`), не wikilink.
- Кожна нота має ≥1 uplink на свій хаб (футер `> Uplink: [[hub_…]]`) + ≥1 паралель.

## 5. Нова нота = обов'язковий ритуал

1. Файл snake_case з префіксом + повний frontmatter.
2. ≥1 uplink на хаб; хаб отримує рядок-лінк назад.
3. Рядок у `MEMORY.md` у правильному домені: `- [Заголовок](file.md) — гачок`.
4. Кожен факт — з абсолютною датою **ДД.ММ.РРРР**.
5. `librarian.py index --source memory` — частина запису, не «потім».

## 6. Inbox raw→processed

Файл без frontmatter або `status: raw` = черга на обробку. Обробка: витягти сенси
в memory-ноти → у сирому `status: processed` + `processed_date` + блок «Розфасовано
у: [[ноти]]». Сирий файл НЕ видаляти (першоджерело-якір).

## 7. Операції: ingest / query / lint / structure

Кожна операція над бібліотекою = один рядок у `log.md` (append-only, найновіше знизу):
- **ingest** — влити знання (розфасувати inbox, дистилювати, створити/оновити ноту).
  Сирі архіви = IMMUTABLE — лише читати.
- **query** — семантичне пригадування (`librarian search`).
- **lint** — цілісність (`sanitize.py --audit` + семантичний прохід). Lint ФЛАГУЄ
  проблеми людині, не переписує зміст мовчки; авто — лише механічні безпечні правки.
- **structure** — зміна каркаса (хаби, symlinks, нове джерело, масовий rename).

## 8. Дистиляція — анти-галюцинація

Дата на кожному факті · версія кожного інструмента · провенанс-лінк на чат-джерело ·
`⚠️ неверифіковано` замість впевненої прози · сире ≠ факт (перехресна перевірка) ·
сенситивне не покидає сирий шар. Повні правила: `docs/06-distillation.md`.

## 9. Гігієна процесу

- Паралельні сесії пишуть одночасно → re-read файлу перед кожним write.
- Пригадування перед твердженням; доказ запису (шлях файлу) завжди.
- Психологічні `user_*` ноти — не зливати і не переформульовувати, лише лінкувати.
- `bridge.md` — гарячий стан, перезаписується; `MEMORY.md` — індекс, не звалище.
